# 7. 一步式 vs 两步式：窗口重放（PR #54，2026-10-15 开始，2026-10-17 完成）

> 状态：**完成**，38/38 个窗口，42 条标签条目。2026-10-15 16:53 SGT Claude 周额度用完，停在 27 个窗口；2026-10-17 09:13 SGT 额度恢复后补跑剩下 11 个（9 个未跑 + 2 个之前出错），09:50 跑完；随后用修过的匹配脚本对全部 38 个窗口重新做了 high 档匹配。

## 问题
话题结束时，下面两种做法哪个更好？
- (A) 两步：现有抽取器（deepseek-v4.1-flash）先抽，再由 Haiku 5.5 max 审稿。
- (B) 一步：Haiku 5.5 max 读窗口，一次完成抽取和判断（新记 / 并入 / 不记），提示词与校验见 `src/onepass.ts`。

另外拿两条"只审稿"的结果做参照：同样这些标签条目，用**原来抽出来的那条候选**直接让审稿人判（不重新抽取）：
- astra v4（`eval/curate/runs/v4b_solo.json`，第 6 篇的 astra 单审）
- Haiku 5.5 max（`eval/curate/runs/haiku.json`，第 6 篇的 haiku 行）

## 数据（测试用例）
- 90 条用户标注（`eval/curate/labels/labels90_relabel.json`）里，能重放的只有自动抽取的条目：extract 47 / manual 22 / import 21。
- extract 里有 42 条能找回原窗口和转录，分布在 38 个窗口。其余条目没有窗口，只能比较判断这一步（见第 6 篇）。
- 42 条的标签分布：s30 有用 4 / 部分有用 1 / 没用 10；s60 有用 13 / 部分有用 8 / 没用 6。
- 近邻只用"该窗口当初抽取之前就已在库里、且来自不同会话"的条目，防止标签条目自己充当近邻。

## 方法
1. 重放（Mac 上，在 PR #54 分支的工作区跑；可续跑，跳过 run1.jsonl 里已成功的窗口，出错的窗口会自动重跑）：
   ```bash
   AB_HOME=~/.agentbrain/eval/h_replay node scripts/replay-eval.ts ~/.agentbrain/eval/labels90_relabel.json ~/.agentbrain/eval/replay/run1.jsonl --conc 3
   ```
   每个窗口分别跑 A 和 B，记录产出、耗时、Haiku 费用。`AB_HOME` 是库的副本，脚本只读，不写正式库。
2. 匹配：匹配员（Haiku）判断每条标签条目在 A/B 的产出里有没有表达同一条核心知识的那条。重放时用 low 档；之后用 high 档对**全部 38 个窗口**重新匹配（用 2026-10-15 审查后修过的脚本：匹配员输出不合法时不落盘、续跑重试）：
   ```bash
   AB_HOME=~/.agentbrain/eval/h_replay node scripts/replay-rematch.ts ~/.agentbrain/eval/replay/run1.jsonl ~/.agentbrain/eval/replay/rematch_high_full.json
   ```
   38 个窗口全部得到合法输出，没有 `INVALID`，费用 $0.04。
3. 打分口径（`eval/onepass-replay/compare.py`）：
   - A/B：标签条目被某条产出匹配上（新记或并入都算）= 留下；没匹配上 = 没进库。
   - 只审稿：审稿结论 admit=true（含并入）= 留下。
   - "总对"= 有用/部分有用被留下 + 没用被挡掉。四种做法用同一批 42 条。

## 复现
仓库内数据即可，不需要私有转录：
```bash

  eval/curate/labels/labels90_relabel.json eval/curate/runs/v4b_solo.json eval/curate/runs/haiku.json
# 分 A/B 的明细（需要 jsonl：把 run1-meta.json 的数组逐行写出即可）
python3 eval/onepass-replay/score_replay.py <run1.jsonl> eval/onepass-replay/rematch_high.json
```
- 仓库内的 `run1-meta.json`（40 行：38 个成功窗口 + 2 行 10-15 出错的旧记录）去掉了 A 路径抽取出的原始候选正文（`A.cands`），出错信息只留第一行、本机路径换成 `<path>`。`rematch_high.json` 是全部 38 个窗口的 high 档匹配。用仓库数据和用 Mac 上的私有 `run1.jsonl` / `rematch_high_full.json` 跑 compare.py，输出逐字相同（2026-10-17 用 `diff` 核对）。
- compare.py / score_replay.py 2026-10-17 修了一处计数：同一窗口先出错、后补跑成功时，不再算作出错窗口。

## 结论
1. **一步走比两步走好**：总对 29/42 对 24/42；有用留下 10/17 对 5/17；没用挡掉 16/16 对 13/16。s30 和 s60 两边都是 B 赢。两步走主要输在 flash 抽取漏掉有用内容，后面的审稿救不回来没抽出来的东西。
2. **两种重放都明显不如"只审稿原候选"**（astra 33/42、Haiku 32/42），差距集中在 s60：同一批有用条目，只审稿留下 11–13/13，重放后 B 只有 6/13、A 只有 2/13。短板是**重新抽取时的召回**，不是判断。
   - 这个对比对重放不公平：标签条目本来就是原抽取器抽出来的，"只审稿"等于默认抽取召回 100%。重放产出里和任何原条目都对不上的那部分（B 30 条、A 25 条）没有标签，没计分，里面可能有有用的新条目，也可能是噪音。
3. **只审稿时 Haiku 太松**：s30 的 10 条没用只挡住 3 条（astra 挡住 5 条），"Haiku 只当审稿人"不能直接替代 astra。
4. B 的"没用挡掉 16/16"要打折看：B 有一部分是因为本来就没抽到，而不是识别出"没用"。不过 B 的空产出窗口（4）比 A（8）还少，产出条数相当（67 对 68），说明不是单纯抽得少。
5. 成本：B 的 Haiku 费用约为 A 的 2 倍（$1.31 对 $0.65，A 另有 flash 抽取费用未计入），耗时相当（275 s 对 261 s）。

## 决定
- 就"一步还是两步"这个问题：数据支持**一步式**（2026-10-16 已批准的话题结束一步抽取方案）。
- 一步式默认仍关闭。按 2026-10-16 的约定，要等另一项话题窗口评测也出结果、两项都显示更好后再由用户决定是否打开。
- 下一步该提高**抽取召回**（例如把整段话题窗口和更多前文给模型、提示词里明确"宁可多提候选"），而不是再加审稿层。

## 保留意见
- 匹配员本身是模型，会判错（稳定性见上，两次 high 匹配 61/62 一致）。
- 42 条样本小；s30 只有 5 条有用/部分有用，s60 只有 6 条没用。
- 只比较了标签条目是否被留下，没有评估重放产出里的新条目。
- 窗口转录和候选原文是私有内容，只在 Mac `~/.agentbrain/eval/replay/`。
