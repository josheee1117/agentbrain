# 评测 14：关联召回实现验收（§11.6 (i)(ii)(iii) + why 重复修复）

日期 2026-10-19。代码分支 `feat/linked-recall`（叠在 PR #59 上）。设计见总体设计 §11.6（PR #61 里已标"已批准，实现中"），前置评测见 [13-linked-recall.md](13-linked-recall.md)。

## 一句话结论

搜索层面确实变好了，而且和评测 13 的预测一致：留出的测试题里，`ab search` 一次就把答案要的条目全拿到的，偏关联的 17 题从 9 → 14，无偏的 13 题从 5 → 11。
但交给模型去答题时，提升小得多：同样 30 道测试题，答全的从 22 → 23（deepseek）和 19 → 24（glm）；覆盖的槽从 61 → 63 和 59 → 63（满分 70）。
原因是改动前模型已经能从 `ab get` 的向量近邻、正向关联里拿到不少东西，而且裁判本身有 ±1 槽的误差（见"抽查"）。所以能说的是：方向是对的，不是变差，输出只多了约一成；答题层面的提升是小幅的，不能说"大幅提升"。

## 改了什么（用户 2026-10-19 批准的范围）

| 项 | 改动 |
|---|---|
| (i) 第 9–16 名 | `ab search` 取 16 条（`SEARCH_MAX_HITS`，代码常量）；前 8 条照旧全文，第 9–16 名每条一行（id、范围、种类、正文前 60 字）。混合检索本身一行没动（§11.4）。 |
| why 重复 | 搜索结果正文改用投影里的正文，不再用索引文本（正文 + why），why 只打一遍。这是 #59 里带进来的显示 bug。 |
| (ii) 双向关联 | 新 `src/links.ts`：补充（refines）、并入（merged_into）、纠正（supersedes）、冲突（conflicts_with）两个方向都算，对方已归档、已被替代也列并标状态。`ab search` 前 8 条每条下面一行"关联:"（最多 3 个，多的提示用 `ab get`）；`ab get` 一个"关联:"块，每个对方一行带正文第一行。只列 id + 一句话，不把对方变成结果行，也不沿关联继续走（和评测 08 的结论一致）。关联里列过的不再进向量近邻。 |
| (iii) Pensieve 原文件 | `ab get --expand` 对 Pensieve 导入条打开导入时记下的 md（主路径不在就试副本路径）。只读记下的 `.pensieve/` 目录里的 `.md`，真实路径必须还在那个目录里（防符号链接指到外面），用同一个文件描述符读，256KB 上限，脱敏，4000 字截断，内容哈希和导入时不同就说明。读不到给原因（不存在 / 没权限 / 拒绝读取），不报错退出。 |

没做：§11.6 第 4 项（抽取提示词记被否掉的方案），用户说先不做。

## 方法

### 搜索层（真实 CLI 输出）
- 库：Mac 正式库的新 `sqlite3 .backup` 副本（store.db、index.db，2026-10-19 16:16），`AB_HOME` 指向副本，用完删除。
- 改动前 = fd75d6b（PR #59 头）的 `src/`；改动后 = 本分支的 `src/`。都用真实 CLI 跑：`node src/cli.ts search <查询> [--project <项目>]`，再对前 3 条全文行跑 `ab get`。
- 记录实际显示出来的 id：改动前 = 8 条全文行；改动后 = 8 条全文行 + "关联:"行里的 id + 第 9–16 名。
- 题目：评测 13 的两组（偏关联 34 题、无偏 43 题），tune/test 划分不变，没改任何题、槽和标注。
- 打分：和评测 13 的 `score_linked.py` 同一套槽定义；"理由"槽只认全文行（一行版和关联 id 不显示 why），前后口径一样。

### 答案层（打分规则先提交：`eval/linked-recall-impl/rubric.md`，提交 0f59da7，早于任何答案层调用）
- 只用测试题：偏关联 17 + 无偏 13 = 30 题。
- 每题把改动前 / 改动后的"`ab search` 输出 + 前 3 条 `ab get` 输出"交给模型，要求只根据输出回答。
- 回答模型：pi `cpa/deepseek-v4-pro`、`cpa/glm-5.3`，`--thinking max`，关掉工具、扩展、技能、上下文文件、MCP，不存会话，stdin `</dev/null`，`AB_HOME` 指向空的临时目录。
- 裁判交叉：deepseek 的答案由 glm 判，glm 的答案由 deepseek 判，参数同上。裁判看不到是改动前还是改动后。
- 参数确认：120 次回答和 120 次裁判的 json 事件里，模型都是指定的那个，`thinkingLevel` 都是 `max`。pi 的 models.json 里这两个模型 `max` 都映射到接口的 `max`（之前记的"glm 的 max 被映射成 high"现在已不成立）。有 2 次回答没有返回思考内容（都是 deepseek、改动前），照常计入。2 次裁判输出第一次解析失败，按规则重跑一次后成功，没有 unparsed。

## 结果

### 搜索层：一次 `ab search` 拿全答案要的条目（full / 题数；括号里是覆盖的槽）

| 题组 | 划分 | 改动前 | 只加第 9–16 名 | 只加关联 | 改动后（都加） | 评测 13 预测 |
|---|---|---|---|---|---|---|
| 偏关联 34 题 | **test 17** | **9**（28/39 槽） | 9（30/39） | 14（34/39） | **14**（35/39） | 14 |
| | tune 17 | 13（30/34） | 15 | 16 | 17（34/34） | 17 |
| 无偏 43 题 | **test 13** | **5**（22/31 槽） | 10（28/31） | 8（25/31） | **11**（29/31） | 10～11 |
| | tune 30 | 17（63/80） | 23 | 19 | 23（71/80） | 23 |

- 测试题的数和预测对得上（偏关联 14/17；无偏 11/13，略好于"10"那个口径，等于 §11.6 写的"16 行 + 关联 11/13"）。没有一题变差。
- 前 8 名在 77 题上和改动前完全一样（id 和顺序），说明混合检索没被动到。
- 两项各管一类：偏关联题主要靠关联（9→14），无偏题主要靠第 9–16 名（5→10）。
- 关联行最多列 3 个，没有让这些数比评测 13 的模拟（不限个数）少。

### 答案层：30 道测试题（full / part / none，覆盖槽数满分 70）

- 逐题看：deepseek 3 题变好、2 题变差；glm 5 题变好、1 题变差。
- 裁判标的"答案里有和必需条目矛盾的说法"：deepseek 2 → 0，glm 2 → 1。
- 为什么答案层的提升比搜索层小：改动前给模型的输出里本来就有前 3 条的 `ab get`（向量近邻 3 条 + 正向关联 id），模型能从里面拼出不少；搜索层只数 8 条全文行，低估了改动前。

### 抽查（执行代理对照原文复核 12 条裁判结果）
复核了所有"变差"的题和几条"变好"的题，前后各 6 条。同意 8 条，不同意 4 条：
- 2 条改动前的被判宽了：把别的条目里相近的话算成覆盖了另一个槽。
- 2 条改动后的被判严了：一条答案已经说出了契约升级后 safeParse 整行丢弃，被判没覆盖；一条答案说了"用 gpt-6.1-sol"，被判没覆盖还标了矛盾。

3 个"变差"的题（deepseek 的 L10、RD27，glm 的 L22）全都和这几条误判有关；另 1 条是一个"变好"的题（RD13）改动前被判宽，让提升显得更小。所以裁判误差大约 ±1 槽，和前后的差距同一量级。答案层只能说"小幅变好、没有变差的迹象"，裁判结果没有改，原样记在 `answer-grades.json`。

真实变好的例子（复核同意）：问"派生维度槽位以前端为准还是后端为准、之前怎么定的"，改动前答"以前没有记录"；改动后关联行列出了已归档的旧规则"以前端为准"（冲突），模型答出了前后变化。

## 独立审查
deepseek-v4-pro（max，只读工具）审了 diff，没有高严重度问题。处理如下：
- 中：`--expand` 读文件时权限不够或文件刚被删会崩。**已修**：给出原因，不崩。
- 低：`.pensieve` 校验只看路径里有没有这个目录名，符号链接能指到别处。**已修**：真实路径必须在记下的那个 `.pensieve` 目录里，用同一个文件描述符读。
- 低：`ab get` 里并入 / 冲突 / 替代各显示两遍。**已修**：去掉旧的状态行，只留撤销提示。搜索行尾的"（有待确认的纠正）"和关联行里的"与 [x] 冲突"并存，没改，前者是警示。
- 低（测试漏洞）：已归档条可能混进第 9–16 名、排序没有回归测试、why 测试只走了降级路径、`expandImport` 分支没覆盖。**都补了测试**。排序的主要证据是真实库上 77/77 题前 8 名不变。

## 局限
- 答案层只有 30 道测试题、一个裁判一次判定，误差和差距同一量级（见抽查）。
- 题目和标注沿用评测 13，偏关联那组本身就偏向显式关联（见评测 13）。无偏那组更能说明真实情况。
- 改动后跑答案层用的是审查前的代码（0f59da7）。审查后 `ab get` 少了 3 行重复状态行，`ab search` 输出逐字不变（77/77 题，重跑核对过），所以没重跑答案层。

## 复现
脚本在 `eval/linked-recall-impl/`，题目和 `props-meta.json` 在 `eval/linked-recall/`（PR #61）。
```
# Mac，库副本
C=~/.agentbrain/eval/links14; mkdir -p $C/db $C/out
sqlite3 ~/.agentbrain/store.db ".backup '$C/db/store.db'"; sqlite3 ~/.agentbrain/index.db ".backup '$C/db/index.db'"; cp ~/.agentbrain/embedding.json $C/db/
# before/after = 两个版本的 src/ + package.json（node_modules 软链）
AB_HOME=$C/db node cli-run.ts $C/db $C/out <before> <after> linked-queries.json r95-multi.json
AB_HOME=$C/db node expand-check.ts <after> $C/db
AB_HOME=$C/db node gold-dump.ts <after> $C/db $C/out/gold.json linked-queries.json r95-multi.json
AB_HOME=<空临时目录> python3 answer.py $C/out answer; AB_HOME=<空临时目录> python3 answer.py $C/out judge
python3 score_answers.py $C/out
# 搜索层打分（box 或 Mac）
python3 score_impl.py eval/linked-recall ids.json
rm -rf $C
```
仓库里只有 id 和打分结果（`ids.json`、`scored.json`、`answer-grades.json`），没有正文、答案原文和工具输出。
