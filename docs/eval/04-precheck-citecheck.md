# 4. 无信号窗口预检（#47）与引用核验（#48）（2026-10-14）

两项都是"上线前用真实库副本量一下"的检查，没有标注集。

## 4.1 预检：无信号窗口跳过 LLM 抽取（#47，5f89112）

**问题**：在 LLM 抽取前，用便宜的规则（`hasExtractableSignal`）跳过没有内容的窗口，会不会把有内容的窗口也跳过？

**数据与方法**：
- Mac 真实库副本，408 个会话切出 403 个窗口。
- 每个窗口跑一遍 `hasExtractableSignal`，统计跳过多少。
- 对其中 206 个已经抽取过的窗口，检查被跳过的窗口当初有没有产出（proposal、attachment、correction）。

**结果**：
- 跳过 3/403（0.7%），分别是 `/clear`、`/model` 和"你好"。206 个已抽取窗口里同样跳过 3 个，它们当初都是 0 产出。
- 第一版规则更宽，跳过了 11 个（2.7%），其中有只含助手汇报的窗口和长 `<task>` 提示词。之后收紧了。

**决定**：2026-10-14 11:44 合并。

**保留意见**：省下的 LLM 调用只有 0.7%，主要价值是不给明显空的窗口花钱。

## 4.2 引用核验：召回时检查代码引用是否过时（#48，80bd922）

**问题**：对做过代码核验的条目，召回时重新检查引用的文件和原句是否还在，延迟能否控制在 5 ms 预算内？能不能真的发现过时条目？

**数据与方法**：
- Mac 真实库副本里 23 条 active 的代码核验条目。
- 逐条跑 `citecheck.citationsStale`，记录每条耗时，并人工看被标为过时的条目。

**结果**：
- 2/23 被标"可能过时"（059aeb97、fe0c7fa8）。两条引用的召回代码都在 #37～#39 重构时移动过，判断为真实漂移。
- 每条耗时 p50 0.32 ms、p95 1.84 ms、max 1.87 ms。

**决定**：2026-10-14 11:45 合并。失败的条目进 `verify_queue`，由后台 `verifyPass` 优先复核；超时或出错一律放行（fail-open）。

**保留意见**：
- 样本只有 23 条，没有做误报率标注。
- `verifyPass` 的队列路径没有单测。

**复现**：两项都需要库副本和当时的提交（5f89112、80bd922），没有单独的评测脚本，数字来自 PR 描述。
