# 6. 审稿（`ab curate`）：多模型评审团 vs 单模型（PR #54，2026-10-14～15）

## 问题
抽取结果先进候选区，再让审稿模型按《好记忆的标准》（`docs/good-memory-standard.md`，即 `src/standard.ts`）判断 keep / rewrite / merge / discard。要回答：
1. 三家模型独立判、一致即执行、分歧交仲裁（panel 模式），能不能达到"没用的丢掉 ≥90%、有用的留下 ≥85%"？
2. 一个主审 + 参考意见（primary），或单个模型独判（solo），会不会更好？
3. 标准 v3→v4 的修改是否有效？

## 方法
- 评测脚本 `scripts/curate-eval.ts` 在 PR #54 的分支里（`feat/v3-phase2-curate`）：在库副本（`AB_HOME` 指向副本）上对标注条目跑 dry-run 审稿，输出每条的结论。
  ```bash
  AB_HOME=<库副本> node scripts/curate-eval.ts labels90.json out.json [s60]   # 在 PR #54 分支上跑
  ```
  当时的批量脚本在 `eval/curate/scripts/`（`run_v3.sh`、`run90.sh`、`runv4.sh`、`runcli.sh`）。`rearb.ts` 用于对 v6 中 7 条仲裁失败的条目、用同样的三家判决重跑仲裁，结果是 v6r。
- 每家模型并发 1；遇到 429 就退避重试，额度用完就停下。
- 打分：
  ```bash
  cd eval/curate && python3 scripts/score_runs.py > scores.md
  ```
  `runs/*.json` 是压缩后的运行结果：summary 加上每条的 id、标签、route、final、admit、各家投票。改写文本没有保留。
- 指标：
  - 没用的丢掉：没用条目中 admit=false 的比例。
  - 有用+部分有用的留下：admit=true（merge 算留下）的比例。
  - 另一口径"没新增"：merge 只把候选归档、不改目标条目，按"库里没多一条"来算。

## 结论与决定
- 10-15 上午（v5、v6 之后）：没有一种配置达标。同一提示词跑两次就能差 ±13 个百分点。为免过拟合，停止按单条调提示词。评审团合议（80/80）不如 astra 单家（87/87），而实际定去留的基本是仲裁那一家。
- 10-15 约 10:30：用户决定由 astra 一人拍板，其他模型只给参考（primary 模式）。在 s60 上，参考意见没有带来提升（p1 和 solo1 几乎一样），v6 评审团比 astra 主审更差。
- 10-15 11:50：根据 s60 的漏判规律提出标准 v4，PR #54 commit c2ef813。v4 有三处改动：
  - 项目知识不因"能查到"而丢；
  - 通用技术常识和凭据套话不记；
  - 派活提示里的通用干活方法按内容判断。

  结果是留有用升到约 90%，丢没用约 60%。
- 10-15 14:10：用户确认"转述的通用干活方法要留"，据此改标 2 条；默认改成 astra 单独判（e3f2a46）。
- 10-15 14:57（用户经 pstack review 认可）：默认路径不再用多模型评审团、仲裁或参考意见。认领/租约那套多审稿基础设施撤掉（5e7f6b2）。目标设计改为：话题结束时，由一个后台模型（Claude Code 下用 Haiku 5.5 max）读窗口、标准和附近已有记忆，一次决定新记 / 并入 / 不记。下一步评测见第 7 篇。
- 剩下的误留，多数是 merge（并入近邻）和 rewrite（把具体的坑概括成"契约"）。Haiku 和 astra 是同一种毛病。
